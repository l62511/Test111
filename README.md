# 订单客服 Agent

基于 **LangChain + MCP + ReAct** 的电商订单客服智能体，配一套面向商家的可视化后台。

顾客侧是对话入口（命令行 / 网页）：能查订单、查售后进度、取消订单、提交退款、问经营数据。
商家侧是浏览器后台：人工审核中心、Agent 会话观测、商品售后分析、运行与操作审计。

业务规则、身份校验、退款金额、走自动还是转人工，全部在服务端裁决，模型只负责理解意图和编排调用。

## 设计立场

这个项目把绝大部分精力放在「模型不该有能力做的事」上，而不是「让模型更聪明」。

- **身份不进工具 schema**。`user_id` 在五个工具的参数里根本不存在，模型无从伪造，也就谈不上被提示词注入绕过。
- **金额不由模型决定**。工具入参里没有「最终退款金额」这个字段，模型只能传「用户主张退多少」，
  实际金额由规则引擎按实付、已退、问题类型算出来。模型想多退，没有入口。
- **通道不由模型选择**。未发货的低风险单自动放款，发过货的一律进人工队列——
  这是代码里的硬规则，不是提示词里的一句请求。
- **业务规则在服务层**，不靠提示词约束。取消只能一次、退款额度累加、越权不可见，全部由服务层的持锁事务保证。
- **审批闸门在商家后台**。提交申请不等于放款，钱只有在商家点「通过」的那一刻才动。
- **每一步都留痕**。用户说了什么、模型调了什么、工具返回什么、谁批的、批之前凭什么判定，全部可回溯。

一句话概括：**让模型做它擅长的，让系统做它必须做的。**

## 功能

| 能力 | 说明 |
|---|---|
| 订单与售后查询 | 只读。订单详情、状态、退款记录、售后申请、用户历史售后画像，范围强制限定为本人 |
| 智能退款处理 | 规则引擎按 12 条规则打分，低风险自动放款，高风险转人工；**金额由引擎计算** |
| 人工审核中心 | 待审队列按提交顺序排队；审核详情展示订单、退款历史、Agent 判断依据、审核记录 |
| 售后数据分析 | 退款金额、退款率、原因分布、商品退款排行、异常订单；支持自然语言提问 |
| 运行与操作审计 | 用户指令、Agent 思考、工具调用与结果、异常、人工操作，按序留痕 |
| 累计退款 | 订单记录已退金额，分次退款累加，**累计绝不超实付** |

## 快速开始

### 1. 装依赖

```bash
python -m venv .venv
# Windows
.venv/Scripts/python.exe -m pip install -r requirements.txt
# macOS / Linux
.venv/bin/python -m pip install -r requirements.txt
```

> 需要 Python 3.11+（开发环境为 3.13）。

### 2. 配置

复制 `.env.example` 为 `.env` 并填写：

```ini
# 任何 OpenAI 兼容端点都可以
LLM_API_KEY=your-api-key
LLM_BASE_URL=https://api.example.com/v1
LLM_MODEL=your-model-name

# 数据目录
ORDER_DATA_DIR=data

# 后台会话签名密钥，生产环境务必修改
MERCHANT_SECRET=change-this-in-production
```

不确定该用哪个模型名时，先探一下：

```bash
python scripts/probe_model.py
```

它会列出端点上的可用模型，并逐个验证是否支持 function calling（ReAct 依赖这个能力）。

### 3. 初始化数据

```bash
python -m data.seed
```

会生成 4 个账号、9 笔订单、3 条退款记录。

> 仓库里的 `data/*.json` **是有意提交的**，所以克隆下来不跑这步也能看到完整数据形态。
> 代价是跑完 demo 后 `data/*.json` 会被改写、工作区变脏。想回到初始状态，
> 重跑 `python -m data.seed`，或者 `git checkout -- data/` 丢弃改动。
> 同理，`.preview/*.html` 是后台界面的离线快照（CSS 已内联），
> 不启动服务也能用浏览器直接打开核对界面。

### 4. 启动

**顾客端**（另开一个终端）：

```bash
python -m agent.main
```

会提示输入账号密码。调试时可以用 `--as u_1001` 跳过登录：

```bash
python -m agent.main --as u_1001
```

**商家后台**：

```bash
python -m web.app
# 或指定端口
python -m web.app --port 8080
```

打开 http://127.0.0.1:8000 即可。

## 五个工具

工具的 description 里写了四要素：功能、前置条件、返回内容、**不可调用场景**。最后一项是刻意设计的——比起告诉模型「什么时候用」，告诉它「什么时候不要用」更能减少误调用。

| 工具 | 读/写 | 必填 | 可选 |
|---|---|---|---|
| `query_order` | 只读 | — | `order_id`、`status`、`limit` |
| `query_after_sales` | 只读 | — | `order_id` |
| `query_sales_analytics` | 只读 | — | `period`、`dimension` |
| `cancel_order` | 写 | `order_id` | `reason` |
| `submit_refund` | 写 | `order_id`、`reason`、`issue_type` | `requested_amount` |

**注意 `submit_refund` 没有 `amount` 参数。** 它只有 `requested_amount`（用户口头主张的金额），
用于记录诉求和校验上限，不参与最终金额计算。工具描述里明确写着「金额不由你决定」，
最终退款额由规则引擎返回在 `amount` 字段里，模型只能转述。

返回值里 `result` 说明走了哪条通道：`REFUNDED`（规则判定低风险，已自动放款）
或 `PENDING`（转人工，进队列等待，`queue_position` 是排队位置）。
模型据此决定是报「已退款」还是「已提交，等待商家审核」。

五个工具都挂了 MCP 官方 annotations：三个查询工具标 `readOnlyHint` + `idempotentHint`，
两个写工具标 `destructiveHint`。

## 业务规则

### 状态机

```
CREATED ──pay──▶ PAID ──cancel──▶ CANCELLED ──refund──▶ REFUNDED
                  │                    ▲
                  └──ship──▶ COMPLETED ┘（签收后也可申请退款）
```

### 退款判定：规则引擎说了算

`mcp_server/rules.py` 是纯函数：同样的订单同样的历史，任何时候算出来都一样。它做三件事。

**一、算金额。** 用户主张的金额只作为诉求记录，最终金额 = `min(主张金额 or 可退余额, 可退余额)`。
引擎会把算法写进 `amount_reason`，审核页直接展示「为什么是这个数」。

**二、打分。** 命中规则累计分值，每条规则都带编号、名称、加减分和一句人话依据：

| 规则 | 触发条件 | 分值 |
|---|---|---|
| R10 未发货 | 未发货 | −35 |
| R11/R12 已发货 / 已签收 | 物流节点 | +10 / +20 |
| R13/R14 高价值 / 中大额 | 实付 ≥3000 / ≥1000 | +20 / +10 |
| R15 小额退款 | 本次 ≤100 | −10 |
| R16 非首次退款 | 该订单已退过 | +20 |
| R17/R18 频繁 / 首次 | 近 30 天 ≥2 次 / 无记录 | +15 / −10 |
| R19/R20 签收过久 | >30 天 / >7 天 | +30 / +15 |
| R21 需凭证 | 破损/质量/与描述不符 | +5 |
| R23 签收后全额退 | 已签收且退满 | +15 |

分值 ≥30 高风险（P0），≥10 中风险（P1），其余低风险（P2）。

**三、定通道。** 这里有一条不能让步的硬规则：

```
                     ┌── 未发货 且 分数 < 30 ──▶ 自动放款
                     │                          result=REFUNDED
submit_refund ───────┤
                     └── 发过货（不管分数多低）──▶ 转人工
                              │
                              ▼
                        生成 PENDING 申请
                              │
                     ┌────────┴────────┐
                     ▼                 ▼
                商家通过           商家驳回
                累加金额           订单锁定
                result=APPROVED    result=REJECTED
                                   （需人工解锁）
```

「发过货一律人工」是代码里的 `if shipped: decision = MANUAL_REVIEW`，
不是提示词里的一句请求——风险分再低也绕不过去。

### 金额累加

这是这套系统的核心约束。订单上记 `refunded_cents`，每次退款前校验：

```
已退金额 + 本次金额 ≤ 订单实付
```

支持多次部分退款。举例：iPad 实付 ¥4,799，先退 ¥1,000，再退 ¥500，累计 ¥1,500，余额 ¥3,299。第三次想退 ¥5,000 会被拦下并提示「最多还能退 ¥3,299」。

省略 `amount` 参数表示退剩余全部余额，不是退全额——这个语义差别在提示词和工具描述里都写清楚了。

退到余额为 0 时，订单状态自动置为 `REFUNDED`。

### 约束怎么保证

| 规则 | 实现手段 |
|---|---|
| 只能操作自己的订单 | 查询按 `owner_id` 过滤，写入前校验归属 |
| 取消只能一次 | `cancelled_at` 非空即拒绝 |
| 退款须已取消或已完成 | 状态白名单 `REFUNDABLE_STATUS` |
| 累计不超实付 | 每次退款前计算余额，审批时再校验一次 |
| 并发不重复提交 | 文件锁内读-改-写，进锁后二次检查 PENDING |
| 并发不重复审批 | 审批时在锁内检查状态必须仍为 PENDING |
| 驳回后不可重提 | `refunds.json` 里的 locks 记录 |

越权统一返回「订单不存在」而不是「无权限」——否则别人能拿订单号试探系统里存在哪些单。

## 商家后台

六个页面，服务端渲染 + 原生 CSS，没有前端构建步骤，也不依赖任何图表库——
图表用 CSS 进度条和柱状图拼出来，打开浏览器就能看。

**人工审核中心** `/queue`
按提交顺序排队，显示排队号、等待时长、风险等级与优先级。每张卡片包含：商品、用户、
申请编号、订单实付、已退、**用户主张金额**与**系统判定金额**（两者分开展示，
一眼看出系统有没有采纳用户诉求）、双色进度条、Agent 判断摘要。
高风险卡片左侧有红色标记，需凭证的会打标签。

**审核详情** `/review/{refund_id}`
左侧是订单全貌与该订单的退款历史（含本单在历次申请中的位置）；
右侧是 **Agent 判断依据**：风险等级、风险分、金额算法、逐条命中规则（含加减分与说明）、
审核记录时间线。底部是该用户的其他售后记录，用来判断是不是高频退款用户。
通过/驳回按钮就在这一页，不需要来回跳。

**Agent 会话观测** `/chat`
选一个顾客身份直接和 Agent 对话。每条回复下方可展开 **ReAct 步骤时间线**：
思考 → 工具调用（含参数）→ 工具结果（成功/失败）→ 最终回复。
遇到需要确认的写操作（取消订单），页面会弹出确认卡片，确认后才真正执行。
左侧是历史会话列表，CLI 产生的会话也会出现在这里。

**商品售后分析** `/analytics`
KPI 卡片（退款金额、退款率、金额占比、待审批、自动/人工笔数）、
商品退款排行（带条形图和单商品退款率）、退款原因分布、近 14 天趋势柱、
异常订单表（每条都有可核对的依据）。

**运行与审计** `/audit`
按时间倒序列出全部事件，可按会话、类型、状态筛选，每条可展开原始 JSON。
统计条显示事件总数、今日、工具调用数、人工操作数、异常数、会话数。

**退款记录** `/refunds` 与 **订单** `/orders`
保留原有的全量视图，退款记录新增风险列并可直接点进审核详情。

顶部四个统计卡片：待审批、本月退款金额、本月退款率、高风险待审。

登录态是签名 cookie（HMAC-SHA256），8 小时过期，密钥来自 `MERCHANT_SECRET`。

## 数据存储

五个 JSON 文件在 `data/` 下，由 `ORDER_DATA_DIR` 指定目录：

| 文件 | 内容 |
|---|---|
| `users.json` | 账号、密码哈希、角色 |
| `orders.json` | 订单，含 `refunded_cents` 累计已退 |
| `refunds.json` | 退款申请、规则判定、审核记录与历史、驳回锁 |
| `audit.json` | 审计事件流，只追加，`seq` 单调递增 |
| `sessions.json` | Agent 会话与消息历史（含每条回复的 ReAct 步骤） |

JSON 文件不像数据库那样自带事务，所以这里自己补了两件事，都在 `mcp_server/store.py`：

1. **跨进程互斥锁**：每个文件配一个 `.lock` 伴生文件，Windows 用 `msvcrt`，Unix 用 `fcntl`。Agent 的 MCP 子进程和商家后台是两个独立进程，会同时读写同一份文件——没有文件锁就会丢更新。
2. **原子替换**：先写同目录临时文件，再 `os.replace` 覆盖。同一文件系统内这是原子操作，读者要么看到旧内容，要么看到新内容，不会读到写了一半的 JSON。

`store.transaction()` 把「加锁 → 读取 → 修改 → 原子写回」包成一个上下文管理器，异常时丢弃改动不落盘。

**锁顺序固定为 `REFUNDS → ORDERS`。** 退款提交和商家审批都要同时改这两个文件，
如果一个先锁订单、一个先锁退款，两个进程就会互相等待（ABBA 死锁）。
代码里两条路径都按同一顺序嵌套加锁，这一点改代码时很容易破坏，注释里标了。

> 这套机制在单机多进程场景下是可靠的。如果要横向扩展到多台机器，JSON 文件就不是合适的选择了，应该换成支持事务的数据库。

## 运维命令

```bash
# 查看退款记录（含累计金额、审批人、锁定状态）
python scripts/show_trace.py
python scripts/show_trace.py --order ORD20261010007
python scripts/show_trace.py --status PENDING

# 驳回锁定后，运营复核完解锁
```

## 关键实现决策

**为什么用 JSON 文件而不是数据库？** 按需求选择了文件存储，好处是数据可直接阅读、便于演示和排查。代价是失去了数据库的事务和并发控制，所以用文件锁 + 原子写补上。这个取舍在单机多进程场景成立，跨机器部署就需要换回数据库。

**为什么身份要放在子进程环境变量里？** 因为模型能控制的只有工具参数。参数里没有 `user_id`，提示词注入就没有着力点。

**为什么退款要拆成「申请」和「放款」两步？** 因为审批是一个跨越人工环节的异步过程。如果一次调用里既提交又放款，中间没有可插入的环节，钱就绕过了人。

**为什么审批放在独立的后台而不是终端？** 商家和顾客不在一台机器上。「终端里按 y」只是演示手段，真实场景里审批人是运营人员，需要一个能登录、能排队、能留痕的界面。

**为什么 MCP 用长连接？** `get_tools()` 是无状态的，每次工具调用都会重新拉起子进程并初始化协议。实测 3 次调用从 8.82 秒降到 0.02 秒（`client.session()` + `load_mcp_tools`）。

## 已知限制

- **身份仍是「注入 + 会话」，不是完整认证**。顾客端密码校验后把 `user_id` 注入子进程，商家端用签名 cookie。生产环境应换成 JWT/OAuth，并接入真实的用户体系。
- **网页会话页允许商家代顾客发起对话**。这是为了核验 Agent 行为而做的观测入口，不是真实的顾客登录链路。
- **挂起中的写操作不落盘**。网页端等待确认的取消操作存在进程内存里，服务重启后需重新发起。历史消息不受影响，都在 `sessions.json` 里。
- **JSON 存储不适合横向扩展**。文件锁只在单机多进程内有效。
- **审批队列没有分页**。后台一次最多渲染 100 条。
- **没有通知机制**。用户提交申请后不会收到推送，只能自己查进度。
- **风控规则是静态的**。12 条规则的阈值写死在 `rules.py`，没有按商品类目或用户分层动态调整。
- **分析按商品名聚合**。同一商品的不同型号（如「iPad Air 11 128GB」和「256GB」）如果名称不同会被当成两个商品。
- **会话密钥默认值不安全**。`MERCHANT_SECRET` 未配置时用了固定的演示密钥。
